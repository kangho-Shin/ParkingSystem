# 장치 종류별 번호 체계 및 보존형 DB 마이그레이션 설계

## 목적

시험 현장 `sitenum=9001`, `groupnum=2`의 장치 식별자를 장치 종류별 범위로 통일한다. 기존 MySQL 테이블과 운전 데이터를 삭제하거나 테이블을 재생성하지 않고, 기존 장치 기본키를 새 체계로 안전하게 이전한다.

## 확정 장치 체계

| 장치 | deviceid | devicenum | laneid | 비고 |
|---|---:|---:|---:|---|
| KIOSK 1 | 2001 | 201 | 9020 | 2000번대 / 200번대 |
| 입차 JPXLPR 1 | 4001 | 401 | 9010 | 4000번대 / 400번대 |
| 출차 JPXLPR 1 | 4002 | 402 | 9020 | 4000번대 / 400번대 |
| 입차 JPXLPR 2 | 4003 | 403 | 9010 | 기본 비활성 |
| 출차 JPXLPR 2 | 4004 | 404 | 9020 | 기본 비활성 |
| LDM 1 | 5001 | 501 | 9020 | 5000번대 / 500번대 |

각 종류는 해당 `deviceid` 천 단위 블록에서 `001~999`, `devicenum` 백 단위 블록에서 순차 증가한다. 외부 프로그램은 계속 `sitenum + groupnum + devicenum`을 사용하고, EdgeService가 DB 내부 `deviceid`로 변환한다.

## 프로그램 변경

- JPXLPR 카메라 설정을 `401~404`로 바꾼다. 기본 활성 장치는 입차 `401`, 출차 `402`만 유지한다.
- KIOSK와 APSMain의 외부 번호는 `201`을 유지한다. DB 내부 KIOSK 키 기대값은 `2001`로 변경한다.
- LPR 처리 후 저장되는 내부 장치키 기대값을 입차 `4001`, 출차 `4002`로 변경한다.
- LDM 연결과 표시 선택에서 사용하는 내부 키를 `5001`로 변경한다.
- 실행 배치, 기본 설정, 단위·통합 테스트 및 현재 상태 문서의 기존 `9101/9201/9301/9401`, LPR `101/201`, LDM `401` 전제를 새 체계로 정리한다.

## DB 마이그레이션

새 idempotent MySQL 스크립트를 추가한다. 이 스크립트는 다음 순서로 한 트랜잭션 안에서 실행한다.

1. 현장 `9001`과 차로 `9010/9020`이 존재하는지 확인·보정한다.
2. 기존 장치 행의 `devicenum` 충돌을 피하기 위해 대상 행을 임시 음수 번호로 변경한다.
3. 새 `deviceid`로 장치 행을 삽입하거나 갱신한다.
4. `parking_event.deviceid`, `parking_session.indeviceid/outdeviceid`, `tperiodinout.indeviceid/outdeviceid`의 기존 키를 새 키로 치환한다.
5. `parking_device_link`는 새 장치 행이 존재하는 상태에서 source/target 링크를 새 키로 복사하고 기존 링크를 제거한다.
6. 참조가 모두 전환된 뒤 기존 장치 행만 제거한다. 테이블과 운전 데이터 행은 삭제하지 않는다.
7. `parking_site_sync.configversion`을 증가시켜 EdgeService가 새 설정을 다시 동기화하게 한다.

스크립트는 여러 번 실행해도 같은 결과가 나와야 하며, 새 키가 이미 존재하는 경우 갱신만 수행한다. 대상 테이블이나 선택적 열이 없는 구형 DB에서도 실패하지 않도록 `information_schema` 기반 조건부 SQL을 사용한다.
새 `deviceid` 또는 `devicenum`을 대상 종류가 아닌 다른 장치가 이미 사용 중이면 임의로 덮어쓰지 않고 오류로 중단한다.

## 테이블 보존 원칙

- 모든 MySQL 생성 스크립트는 `CREATE TABLE IF NOT EXISTS`를 사용한다.
- `DROP TABLE`, 테이블 이름 변경 후 재생성, 전체 데이터 비우기를 사용하지 않는다.
- 기존 `000_full_schema.sql`은 신규 설치와 기존 설치 모두에서 테이블을 보존한다.
- 순차 마이그레이션 `001`, `002`, `005`, `006`의 일반 `CREATE TABLE`도 `IF NOT EXISTS`로 변경한다.
- 새 열·인덱스·제약 추가는 기존 마이그레이션처럼 존재 여부를 확인하는 조건부 `ALTER TABLE`을 사용한다.

## 검증

- SQL 정적 검사: 모든 `CREATE TABLE`에 `IF NOT EXISTS`가 있으며 `DROP TABLE`이 없어야 한다.
- 장치 매핑 테스트: KIOSK `201 -> 2001`, LPR `401 -> 4001`, LPR `402 -> 4002`, LDM `501 -> 5001`.
- JPXLPR 파일명 테스트: 입차 세 번째 필드 `401`, 출차 세 번째 필드 `402`.
- 저장소 테스트: 입출차 사건과 세션의 내부 `deviceid`가 `4001/4002`로 저장된다.
- 마이그레이션을 두 번 실행해 결과가 동일하고 기존 주차 세션 수가 변하지 않는지 확인한다.
- 전체 빌드 및 전체 테스트는 기능 구현이 모두 끝난 뒤 한 번에 실행한다.

## 범위 제외

- `sitenum`, `groupnum`, `laneid` 체계는 변경하지 않는다.
- 외부 계약에서 DB `deviceid`를 직접 전달하도록 되돌리지 않는다.
- JPXLPR에서 제거한 REST, UDP, LocalSocket, LDM 및 DB 직접 접근 기능을 복구하지 않는다.
